# REG.RU S3 commands

`regru s3` manages REG.RU object-storage service metadata, bucket lifecycle,
provider quota and access mode, S3 bucket configuration, and key-set metadata.
It deliberately does not list, upload, download, copy, presign, or delete
objects.

## Two provider surfaces

REG.RU does not expose the complete lifecycle through one AWS-compatible API.
The implementation keeps the two contracts separate:

| Surface | Operations |
| --- | --- |
| Authenticated REG.Cloud control plane | Service and bucket inventory, supported bucket creation and deletion, storage and bucket quota, simplified public/private mode, and key-set lifecycle |
| Signed S3 endpoint | Raw bucket policy, CORS, versioning, lifecycle, and website configuration |

Bucket creation never falls back to S3 `CreateBucket`, which REG.RU currently
marks unsupported. Bucket deletion uses the portal mutation with `force=false`;
`regru` first checks the provider object count and will not recursively delete
objects, versions, delete markers, or multipart uploads.

Private control-plane calls run inside the selected account's isolated browser
session. Every mutation first checks the current GraphQL mutation name and
argument set. Unknown schema or result types fail as
`private_contract_drift`. A mutation is never retried after an ambiguous
response. Instead, `regru` performs an independent inventory read and accepts
the result only when that read proves the exact requested postcondition.
Signed configuration mutations also disable SDK retries; a timeout, `429`, or
`5xx` after submission returns `outcome_unknown` instead of resending the
request.

## Commands

Service and provider inventory:

```text
regru s3 service show
regru s3 service quota set --quota-gb GB
regru s3 bucket list
regru s3 bucket show NAME
```

Provider bucket lifecycle:

```text
regru s3 bucket create NAME [--quota-gb GB] [--access private|public]
regru s3 bucket update NAME [--quota-gb GB | --unlimited] [--access private|public]
regru s3 bucket delete NAME
```

`get` remains an alias of `bucket show`; `configure` remains an alias of
`bucket update`. Create, update, delete, quota, public-access, and credential
mutations require the normal TTY confirmation or `--force`. `--dry-run`
validates flags and local JSON documents without opening a browser, resolving
credentials, or sending a provider request.

Signed S3 configuration operations:

```text
regru s3 bucket policy get|set|delete NAME
regru s3 bucket cors get|set|delete NAME
regru s3 bucket versioning get|set NAME
regru s3 bucket lifecycle get|set|delete NAME
regru s3 bucket website get|set|delete NAME
```

Every `set` command except versioning accepts `--file PATH`. The file must be a
single JSON object no larger than 1 MiB. Versioning uses
`--status enabled|suspended`.

Policy files are raw S3 policy JSON. The other accepted document shapes are:

```json
{
  "rules": [
    {
      "id": "browser-read",
      "allowedMethods": ["GET", "HEAD"],
      "allowedOrigins": ["https://example.com"],
      "allowedHeaders": ["*"],
      "exposeHeaders": ["ETag"],
      "maxAgeSeconds": 3600
    }
  ]
}
```

```json
{
  "rules": [
    {
      "id": "expire-temp",
      "status": "Enabled",
      "prefix": "tmp/",
      "expirationDays": 30
    }
  ]
}
```

```json
{
  "indexDocument": "index.html",
  "errorDocument": "error.html"
}
```

Website configuration may instead contain only
`redirectAllRequestsTo.hostName` and an optional `protocol`. The lifecycle
schema intentionally exposes only the provider-documented conservative subset;
transitions, tags, noncurrent versions, and multipart cleanup remain outside
the verified contract.

When replacing CORS, `regru` preserves the REG.Cloud panel origin
`https://cloud.reg.ru`. This prevents a configuration update from removing the
first-party panel rule REG.RU documents as required.

## Credentials and account routing

The signed adapter first asks the selected account's `credential_process` for
the atomic pair `s3.access_key_id` and `s3.secret_access_key`. If those fields
are not supplied, it may retrieve one existing key pair just in time through
the active portal session. The pair remains in process memory for one command,
is never printed, and owned byte buffers are cleared on close as a best-effort
lifetime reduction.

```text
regru s3 credentials list
regru s3 credentials create --name NAME
regru s3 credentials revoke ID
```

Key listing and creation return metadata only. Secret material remains in the
provider portal and can be retrieved just in time later. If an object store has
multiple key sets, select one in the private user profile:

```toml
[accounts.work.cloud]
environment_id = "opaque-cloud-service-id"
s3_key_pair_id = "42"
```

With one Cloud environment and one key set, both selections are automatic.
Multiple environments fail closed until `environment_id` is set. These values
are private routing identifiers, but they are not credentials and never belong
in a project `.regru/config.toml`.

The endpoint defaults to `https://s3.regru.cloud` and path-style addressing is
always used. The AWS SDK requires a signing scope even though REG.RU does not
publish a named region; the current implementation uses `us-east-1` as the
compatibility default pending the authorized end-to-end verification ticket.
Both values may be overridden only in the private user profile:

```toml
[accounts.work.cloud]
s3_endpoint = "https://s3.regru.cloud"
s3_signing_region = "us-east-1"
```

The endpoint must use HTTPS. There are no endpoint, region, access-key, secret,
cookie, or session flags.
